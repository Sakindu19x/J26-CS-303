2. OBJECTIVE 
2.1 Main Objective 
To develop and evaluate an adaptive approach for detecting multi-label web attacks from HTTP request 
data and correlating related detected events using data-derived contextual criterion weights. 
2.2 Specific Objectives 
• To preprocess and encode the SR-BH 2020 HTTP request data using appropriate text and categorical 
feature representations. 
• To develop and evaluate a One -vs-Rest Logistic Regression model for multi -label CAPEC-based 
web-attack detection. 
• To retain and use relevant contextual information from detected events, including temporal, 
source/identity, target, attack-related information, and detection probabilities where appropriate. 
• To adapt Conditional Rough Entropy and Knowledge Granularity to determine the relative 
importance of correlation criteria from data. 
• To calculate an overall weighted correlation score and group sufficiently related detected events 
using a tuned threshold. 
• To evaluate the detection stage using multi -label classification metrics and compare adaptive 
correlation weighting with a fixed/equal-weight correlation baseline.

3. METHODOLOGY 
3.1 Research Methodology / Design 
This research will adopt an experimental research design to develop and evaluate the Adaptive Web 
Attack Detection and Correlation Model. A quantitative approach is appropriate because the research 
uses a labelled webattack dataset develops a supervised multi‑label machine‑learning model calculates 
numerical contextual similarity and correlation scores and evaluates the resulting outputs using 
quantitative measures. 
The experimental process consists of two stages. The first stage focuses on multi‑label web‑attack 
detection, where HTTP request data are preprocessed and used to train and evaluate a Logistic 
Regression model. The second stage focuses on adaptive contextu al correlation, where contextual 
information retained from detected events is used to calculate similarities and derive data‑driven criterion 
weights, for correlation. 
Development will follow an iterative prototyping approach allowing the preprocessing, detection, 
similarity, adaptive weighting, correlation scoring, threshold selection and event‑grouping stages to be 
implemented and tested incrementally. This approach en ables each stage to be evaluated and refined 
before integration into the Component 1 pipeline.

3.2 Data / Experimental Inputs 
3.2.1 Dataset 
The study will use the SR-BH 2020 multi -label web attack dataset , specifically the 
data_capec_multilabel.csv file, as the primary experimental dataset [1], [2]. The dataset contains 907,814 
HTTP requests represented by 24 request and contextual features and provides CAPEC -based multi-
label annotations for web-attack classification [1], [2]. 
The dataset is suitable for Component 1 because it provides both the labelled HTTP request data required 
for supervised multi-label web-attack detection and contextual information that can be retained for the 
subsequent correlation stage. Relevant fields include info rmation associated with the request, source, 
target, timestamp, URI, and other HTTP-related characteristics available within the selected dataset [1], 
[2]. 
3.2.2 Data Preprocessing and Feature Representation 
Before model development, the dataset will undergo data cleaning, missing-value handling, and relevant 
feature selection. Textual HTTP fields selected for the detection model, such as the URI and request -
body information where available, will be transforme d using Term Frequency -Inverse Document 
Frequency (TF-IDF). Selected categorical features, such as HTTP method and status-related information 
where applicable, will be represented using One-Hot Encoding. 
The prepared dataset will then be divided into training and held -out test data. The training data will be 
used to develop the One-vs-Rest Logistic Regression classifiers, while the held-out test data will be used 
to evaluate detection performance on requests that were not used to fit the classifiers. 
3.3 Detection Stage 
The detection stage will use Logistic Regression with a One-vs-Rest (OvR) approach for classifying web 
attacks that involve labels. Logistic Regression is chosen because it works with high -dimensional and 
sparse data like the kind generated by TF -IDF. It is also efficient enough for the experimental setup 
being used. Another r eason for selecting it is that it gives probability estimates for each attack label, 
which helps in understanding how confident the model is about a prediction. 
Under the One-vs-Rest strategy one binary Logistic Regression classifier will be trained for every attack 
label. Each classifier learns to decide whether an HTTP request belongs to its attack category or not. 
Since these classifiers are trained separately and do 
 not influence each other an HTTP request can get than one attack label assigned. This supports the -
label nature of the SR-BH 2020 dataset [1] [2]. 
For every HTTP request the detection stage will output the predicted attack label or labels along with 
the confidence scores or probabilities. At the time important contextual details, from the original HTTP 
request will be kept. This preserved context ens ures that detected events can be properly passed on to 
the stage. The adaptive contextual correlation stage. Where further analysis can take place.

3.4 Adaptive Contextual Correlation 
After the label detection stage  we will keep the contextual information that belongs to each detected 
web-attack event so that we can do correlation. The correlation dimensions we choose are context 
source/identity context, target context and attack/behaviour context. We will also keep detection 
probabilities or confidence values as supporting information. These values will be used in the correlation 
calculation only if we can show experimentally that they help. 
When we have two detected events, A and B we will compute a similarity value S_i(A,B) for each chosen 
contextual criterion i. The similarity function changes with the type of information we compare. 
Temporal similarity shows how close the event timestamps are. Source/identity similarity shows links 
such as a shared source IP or session when we can find one. Target similarity compares the web resources 
or URIs that the attacks targeted. Attack/behaviour similarity shows how the predicted attack labels or 
behaviours are related. 
We will not set the importance of the selected correlation criteria with fixed weights. Instead the adaptive 
weighting stage will use the method described by Sun, Gu and Chen [4]. That method uses Conditional 
Rough Entropy and Knowledge Granularity to find  how important each alert attribute is from the data. 
Component 1 will adapt that weighting idea to the attributes of the detected HTTP web-attack events.

3.5 Baseline / Benchmark 
To evaluate the effect of the proposed weighting mechanism the adaptive contextual correlation 
approach will be compared with a fixed or equal -weight correlation baseline. Both methods will work 
on the set of detected web -attack events. They will also use the contextual criteria, similarity functions 
and threshold-testing procedure. 
In the baseline method every selected contextual criterion will be given the fixed weight. In the proposed 
method the weights for each criterion will instead be determined from data using Conditional Rough 
Entropy and Knowledge Granularity [4]. The correlation score in both cases will then be computed using 
the weighted similarity formula. 
By keeping all correlation criteria and similarity calculations the same across both approaches the 
comparison is designed to focus on the impact of the weighting method. This setup allows the study to 
check whether adjusting the importance of criteria bas ed on data provides an advantage, over giving 
each criterion the same fixed importance when linking detected web-attack events.

3.7 Validation Strategy 
We will validate the detection stage with held-out test data that were not used during the training of the 
Logistic Regression classifiers. Detection performance will be measured by Precision, Recall F1 -score 
per label Micro and Macro averages and Hamming Loss as defined in Section 3.6. 
In the correlation stage we will compare the proposed weighting approach with the fixed/equal -weight 
correlation baseline. Both approaches will use the detected events, contextual criteria, similarity 
functions and threshold-testing procedure so that the effect of the adaptive weighting mechanism can be 
examined under consistent experimental conditions. 
We will analyse correlation threshold values to find an appropriate threshold for grouping sufficiently 
related detected events. The final criterion,  for assessing the quality of the resulting correlated event 
groups will be set based on the dataset evidence and the finalized experimental validation strategy.

4. HIGH-LEVEL SYSTEM ARCHITECTURE 
4.1 Overview 
Component 1 is an Adaptive Web Attack Detection and Correlation Model. It works with HTTP request 
data to detect types of web attacks. It keeps contextual details and connects related attack events using 
adaptive weights that come from the data itself. 
The process starts with HTTP web -server logs taken from the SR -BH 2020 dataset [1] [2]. These logs 
go through a preprocessing step. This includes cleaning the data dealing with missing values selecting 
features transforming certain text-based features using TF-IDF and converting some categorical features 
using One-Hot Encoding. 
After preprocessing the data is fed into a One -vs-Rest Logistic Regression model. This model detects 
types of web attacks at once. It gives out predicted attack labels, the probability for each label. Keeps 
important contextual information such as the time stamp, the source or identity of the request the target 
or URI and details about the attack or behavior. 
The detected events are then processed in two steps: contextual similarity calculation and adaptive 
weight calculation. Contextual similarities are calculated based on four criteria: time, source or identity, 
target and attack or behavior. At the time Cond itional Rough Entropy and Knowledge Granularity [4] 
are used to derive data-driven weights for each of these criteria. 
These similarities and weights are combined to compute a weighted correlation score, for each pair of 
events. This score is compared to a correlation threshold. If the score is high enough the events are 
grouped together into event groups or scenarios. The final output includes the grouped events their attack 
labels, the grouping information and the relevant context that led to the correlation. 
4.2 Overall Integration 
Component 1 is one part of a four‑piece CTI‑Assisted Digital Forensic Investigation Tool that small and 
medium businesses can use. Component 1 looks for web attacks. Links them together based on the 
context using data from HTTP requests. 
Inside the system Component 1 creates organized correlated findings about web attacks. These findings 
can be combined with the results and analysis from the parts of the research. The organized output from 
Component 1 will contain: 
• detected web‑attack label(s). Associated probability/confidence information; 
• relevant temporal source/identity, target and attack/behaviour context; 
• correlation score; 
• group/scenario identifier; and 
related member events and correlation information. 
Component 1 supplies the part of the research that finds and links web attacks. The other parts handle 
network analysis, CTI‑assisted analysis and forensic investigation. When the outputs from all parts are 
combined the entire system gives more organized i nformation, for investigating cyber incidents and 
digital forensics.
