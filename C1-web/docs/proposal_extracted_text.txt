ABSTRACT 
Small and medium enterprises (SMEs) are relying more on web applications and digital services that are 
connected. They usually have very limited security operations and digital -forensic resources. When a 
cyber incident happens web-attack detections can come in as events. This makes it hard for a small team 
to see which detections are connected. Current methods for detecting web attacks and analyzing logs 
can. Show suspicious events. The way they connect events usually use fixed or set rules. This research 
introduces an Adaptive Web Attack Detection and Correlation Model. This is the part of a tool that helps 
with digital forensic investigations for SMEs. The model uses the SR -BH 2020 dataset that has labels 
for web attacks. It applies steps like preprocessin g, TF -IDF for text fields One -Hot Encoding for 
categories and One -vs-Rest Logistic Regression for detecting attacks. The events that are found keep 
details like time, source, target, attack labels and confidence levels. Then the events are compared using 
how similar they are in context. Conditional Rough Entropy and Knowledge Granularity are used from 
research to create weights for similarity. These weights are added together to make a score. Events that 
meet a level are grouped as related attacks. The model will be tested using measurements like Precision, 
Recall, F1-score, averages and Hamming Loss. The adaptive correlation approach will be compared with 
a fixed/equal-weight correlation baseline to evaluate the effect of data -derived adaptive weighting. The 
model creates attack findings that can be used in the bigger forensic framework. 
Keywords: Multi -Label Web Attack Detection; Adaptive Event Correlation; Logistic Regression; 
Conditional Rough Entropy; Knowledge Granularity.

1. INTRODUCTION 
1.1 Background and Context 
Web applications and online services have become parts of how modern organizations run. Because they 
are on the Internet web applications also face types of web attacks. A single web attack can send bad 
HTTP requests, which create many security events that look separate even though they come from the 
same web attack. 
Machine‑learning can help spot web attacks by finding HTTP requests and telling what kind of web 
attack they are.  Looking at each bad request alone does not show whether several web attacks are 
connected. Web attacks may share details such as when they happened, where they came from what web 
resource they targeted and how the attack behaved. Linking those details give s a picture of web attack 
activity than looking at each event alone. 
This problem is especially important for Medium Enterprises or SMEs which often have less security 
monitoring and fewer people to do digital forensic investigation. When a cyber incident happens the 
many security events can make the investigation harder. Giving security staff a list of related web attacks 
helps them understand and investigate suspicious web activity faster. 
The whole research project, which is called "CTI‑Assisted Digital Forensic Investigation Tool for SMEs 
" wants to help forensic investigators. It combines web attack analysis, network attack analysis, 
CTI‑assisted prioritisation and attack timeline analysis. Inside the project Component 1 – Adaptive Web 
Attack Detection & Correlation Model , it focuses on finding web attacks from HTTP request data and 
linking events 
Component 1 first uses multi‑label machine learning to spot web attacks. Keeps the important context 
for each event of treating each bad request as a single event the component uses an adaptive contextual 
correlation approach. This approach looks at time, source or identity, target and attack behavior to decide 
which web attacks belong together. The grouped events are then given as findings, for the rest of the 
digital forensic investigation. 
Existing Solutions and Their Limitations 
Existing security and web -log analysis solutions provide capabilities for monitoring, analysing , and 
correlating security -related events. Splunk Enterprise Security supports event correlation through 
correlation searches and provides capabilities for identifying related security events for investigation [8]. 
Elastic Security provides SIEM capabilities for detecting and investigating security threats and supports 
different detection rule types, including event correlation rules [9]. GoAccess is an open -source, real-
time web-log analyser that processes web -server logs and provides HTTP statistics and visual reports 
for monitoring web activity [10]. 
Although these solutions provide useful capabilities for web-log analysis, security monitoring, detection, 
and event correlation, the research problem addressed by Component 1 is more specific. The proposed 
research investigates the correlation of multi -label machine-learning-detected HTTP web attacks using 
contextual information retained from the detected events. It considers temporal, source/identity, target, 
and attack/behaviour  context and applies data -derived adaptive weighting using Conditional Rough 
Entropy and Knowledge Granularity [4] when calculating relationships among detected events.

Therefore, Component 1 is not intended to replace existing SIEM or web-log analysis platforms. Instead,

Overall Proposed Solution and the Role 
The overall proposed solution is a CTI-Assisted Digital Forensic Investigation Tool for SMEs. This tool 
is designed to help teams analyze and investigate incidents. It does this by combining the outputs of 
research components. The whole system brings together web‑attack analysis, network security findings, 
CTI‑assisted prioritization and attack timeline analysis. All of these parts give forensic investigation 
teams clearer more structured information. 
Within the system Component 1 – Adaptive Web Attack Detection & Correlation Model is in charge of 
the web‑attack detection and correlation stage. This component reads HTTP request data. Uses 
multi‑label machine learning to spot one or more web‑attack types. It then keeps contextual information 
that comes with the detected events, such as time, source identity, target and attack behaviour so that this 
information can be used for correlation. 
The detected events are compared by using similarity. Conditional Rough Entropy and Knowledge 
Granularity are adapted to produce data‑driven weights that show how important each chosen correlation 
criterion is. These weights are added to the contextual sim ilarity values to compute a correlation score. 
Any detected events that reach the chosen correlation threshold are grouped together related web‑attack 
events. 
The resulting correlated web‑attack findings, including event context detected attack labels and 
correlation information are provided in a structured form for integration, with the subsequent 
components of the overall forensic investigation framework. Comp onent 1 is therefore limited to 
web‑attack detection and adaptive contextual correlation. All other tasks – network analysis, CTI‑based 
prioritization and later attack analysis – are carried out by research components.

1.2 Literature Review 
1.2.1 Multi-Label Web Attack Detection 
Sureda Riera et al. Introduced the SR -BH 2020 -label web attack dataset for classifying web attacks 
based on the Common Attack Pattern Enumeration and Classification (CAPEC) taxonomy [1]. The 
dataset is publicly available via Harvard Dataverse [2]. Include s HTTP request data along with 
contextual information and multi -label attack annotations. In contrast to single -label classification the 
multi-label setup allows one HTTP request to have than one attack label. This makes the dataset well -
suited for studying web attacks that combine attack behaviors. 
The SR -BH 2020 dataset contains 907,814 HTTP requests, each represented by 24 request and 
contextual features [1] [2]. These features keep details from web requests that help machine -learning 
models detect attacks. They also include data that can be used later in analysis. This is especially relevant 
to the proposed research because Component 1 needs both a -label detection step and contextual details 
that can help identify connections between detected events. 
The work of Sureda Riera et al. Shows that machine-learning methods can be used effectively for -label 
CAPEC-based classification of web attacks [1].. Their focus is mainly, on classifying individual web 
requests. It does not address whether multiple malic ious requests are related and should be grouped as 
part of an attack activity. So even if individual requests are classified correctly it does not solve the 
event-correlation problem that Component 1 is focused on. 
 
1.2.2 Security Event and Alert Correlation 
Security monitoring systems often produce separate alerts, which makes it hard to see which alerts 
belong to the same attack.. Colleagues [3] examined alert -correlation techniques that are used with 
Network Intrusion Detection Systems (NIDS). They describe d how correlation helps combine and 
analyse security alerts to aid in cyber -attack analysis and prediction. Their survey shows that it is 
important to move past alerts and instead find connections among security events. 
Colleagues [6] offered an attribute-focused correlation method. They suggested an alert-fusion technique 
that uses grey relation and attribute -similarity correlation. This method looks at alert attributes such as 
attack type, timestamp, source IP address, destination IP address and port details. It measures similarity 
by examining each attribute’s characteristic then mixes the attribute similarit ies and their weights to 
compute a similarity between alerts [6]. 
This work matters for Component 1 because it shows that relationships between security events can be 
judged by comparing contextual attributes instead of just one. In the proposed research the same general 
idea is used for web-attack detection. It looks at time, source/identity, target and attack/behaviour context 
to decide whether detected HTTP events are linked. 
However Component 1 does not use the grey -relation weighting method from Liang and colleagues. 
Instead the research uses a weighting approach that relies on Conditional Rough Entropy and Knowledge 
Granularity [4]. Thus Liang and colleagues mainly support the idea of multi -attribute similarity and 
correlation while Sun, Gu and Chen [4] supply the method, for the adaptive attribute-weighting part.

1.2.3 Contextual Correlation and Web-Attack Reconstruction 
Utomo Studiawan and Pratomo looked into forensic event reconstruction of web attacks using timeline 
generation log decoding and rule-based event correlation [7]. Their method brings together server -side 
web and system log artifacts to build a timeline of security events and uses correlation rules to reconstruct 
-stage attack activities, such as reconnaissance, exploitation and privilege escalation. Their testing using 
the AIT Log Data Set V2.0 shows how correlated log evidence can be used to reconstruct relationships 
between events that happen during a web attack [7]. 
This study is important for the proposed research because it shows the value of looking at relationships 
between web  security events instead of looking at individual log records on their own. Connecting 
contextual evidence can give an organized view of attack activity and help in understanding how multiple 
events are connected. 
However the correlation method used  by Utomo et al. Is rule -based [7]. Component 1 looks at an 
approach to correlation where contextual similarities among multi -label machine -learning-detected 
HTTP attacks are combined using data-derived adaptive weights. Therefore the study strongly supports 
the importance of web-event correlation and reconstruction while also showing the difference, between 
rule-based correlation and the adaptive contextual correlation approach being studied in this research. 
1.2.4 Adaptive Attribute Weighting for Correlation 
Sun, Gu and Chen proposed an alert aggregation method based on Conditional Rough Entropy and 
Knowledge Granularity to address the problem of determining the importance of different alert attributes 
during correlation [4]. Their approach derives attribute weights from the characteristics of the alert data 
rather than depending entirely on manually assigned fixed weights. These weights are subsequently 
combined with attribute similarity values to calculate a similarity between security alerts [4]. 
In their approach  Conditional Rough Entropy and Knowledge Granularity are used to evaluate the 
importance of alert attributes. The resulting attribute weights influence how strongly each similarity 
criterion contributes to the alert similarity. Alerts whose calculated simi larity satisfies the defined 
threshold can then be aggregated as related alerts [4]. The method was evaluated using security -alert 
data derived from CIC-IDS 2018 and DARPA 98 [4]. 
This method provides the foundation for the adaptive weighting mechanism proposed in Component 1. 
However the present research does not claim Conditional Rough Entropy, Knowledge Granularity or the 
underlying weighting method as a contribution. Instead Component 1 investigates the adaptation of this 
data-driven weighting concept, to the correlation of -label machine-learning-detected HTTP web attacks. 
The selected web-event context includes source/identity, target and attack/behaviour  information, with 
the resulting adaptive weights used when calculating the overall contextual correlation score. 
This allows the proposed research to examine whether data -derived adaptive weighting can provide an 
advantage over a fixed/equal-weight correlation baseline when grouping related web-attack detections.

1.3 Research Gap 
Existing research has shown that machine -learning methods can be used to find and sort web attacks 
based on HTTP request data [1] while studies on security event correlation have proven that connections 
between alerts can be found by looking at event detai ls and how similar they are [3] [6]. Research on 
web attack reconstruction has also shown that connecting web and system events helps understand attack 
activities; however these methods often depend on rules that are set in advance [7]. 
Security-analysis platforms like Splunk [8] and Elastic Security [9] also have features for connecting 
events while web-log analysis tools like GoAccess [10] help watch and study web-server activity. So the 
problem is not that there is no way to connect events or look at web logs. The real problem this research 
is trying to solve is how to combine -label machine-learning-based HTTP attack detection with smart 
ways of connecting events. 
Even though Sun, Gu and Chen show that Conditional Rough Entropy and Knowledge Granularity can 
help find out how important different alert features are when grouping alerts [4] their method is not made 
for connecting -label machine -learning-based HTTP web -attack detections using the web request 
information that is kept. Also most research on webattack detection focuses on finding or sorting out bad 
requests instead of figuring out how to weigh the relationships between different detected attacks in a 
smart way [1]. 
So this research looks at using data-based ways to connect multi-label ML-detected web attacks. Time, 
source or identity, target and attack or behavior context are used to look at how the detected eventsre  
connected. Conditional Rough Entropy and Knowledge Granularity are used to find out how important 
the different connection factors are. The new smart way of connecting events is compared with a method 
that gives weight to all factors to see how much bette r the smart weighting is, at grouping similar web -
attack detections.The specific research gap is therefore the limited investigation of data-derived adaptive 
contextual weighting for correlating multi -label ML -detected web attacks. The proposed adaptive 
weighting mechanism will be compared with a fixed/equal -weight correlation baseline under the same 
contextual criteria and similarity functions. 
The research gap is the limited investigation of adaptive, data -derived contextual weighting for 
correlating multi-label machine-learning-detected HTTP web attacks.

3. METHODOLOGY 
3.1 Research Methodology / Design 
This research will adopt an experimental research design to develop and evaluate the Adaptive Web 
Attack Detection and Correlation Model. A quantitative approach is appropriate because the research 
uses a labelled webattack dataset develops a supervised multi‑label machine‑learning model calculates 
numerical contextual similarity and correlation scores and evaluates the resulting outputs using 
quantitative measures. 
The experimental process consists of two stages. The first stage focuses on multi‑label web‑attack 
detection, where HTTP request data are preprocessed and used to train and evaluate a Logistic 
Regression model. The second stage focuses on adaptive contextu al correlation, where contextual 
information retained from detected events is used to calculate similarities and derive data‑driven criterion 
weights, for correlation. 
Development will follow an iterative prototyping approach allowing the preprocessing, detection, 
similarity, adaptive weighting, correlation scoring, threshold selection and event‑grouping stages to be 
implemented and tested incrementally. This approach en ables each stage to be evaluated and refined 
before integration into the Component 1 pipeline.

3.2 Data / Experimental Inputs 
3.2.1 Dataset 
The study will use the SR-BH 2020 multi -label web attack dataset , specifically the 
data_capec_multilabel.csv file, as the primary experimental dataset [1], [2]. The dataset contains 907,814 
HTTP requests represented by 24 request and contextual features and provides CAPEC -based multi-
label annotations for web-attack classification [1], [2]. 
The dataset is suitable for Component 1 because it provides both the labelled HTTP request data required 
for supervised multi-label web-attack detection and contextual information that can be retained for the 
subsequent correlation stage. Relevant fields include info rmation associated with the request, source, 
target, timestamp, URI, and other HTTP-related characteristics available within the selected dataset [1], 
[2]. 
3.2.2 Data Preprocessing and Feature Representation 
Before model development, the dataset will undergo data cleaning, missing-value handling, and relevant 
feature selection. Textual HTTP fields selected for the detection model, such as the URI and request -
body information where available, will be transforme d using Term Frequency -Inverse Document 
Frequency (TF-IDF). Selected categorical features, such as HTTP method and status-related information 
where applicable, will be represented using One-Hot Encoding. 
The prepared dataset will then be divided into training and held -out test data. The training data will be 
used to develop the One-vs-Rest Logistic Regression classifiers, while the held-out test data will be used 
to evaluate detection performance on requests that were not used to fit the classifiers. 
3.3 Detection Stage 
The detection stage will use Logistic Regression with a One-vs-Rest (OvR) approach for classifying web 
attacks that involve labels. Logistic Regression is chosen because it works with high -dimensional and 
sparse data like the kind generated by TF -IDF. It is also efficient enough for the experimental setup 
being used. Another r eason for selecting it is that it gives probability estimates for each attack label, 
which helps in understanding how confident the model is about a prediction. 
Under the One-vs-Rest strategy one binary Logistic Regression classifier will be trained for every attack 
label. Each classifier learns to decide whether an HTTP request belongs to its attack category or not. 
Since these classifiers are trained separately and do 
 not influence each other an HTTP request can get than one attack label assigned. This supports the -
label nature of the SR-BH 2020 dataset [1] [2]. 
For every HTTP request the detection stage will output the predicted attack label or labels along with 
the confidence scores or probabilities. At the time important contextual details, from the original HTTP 
request will be kept. This preserved context ens ures that detected events can be properly passed on to 
the stage. The adaptive contextual correlation stage. Where further analysis can take place.

3.4 Adaptive Contextual Correlation 
After the label detection stage  we will keep the contextual information that belongs to each detected 
web-attack event so that we can do correlation. The correlation dimensions we choose are context 
source/identity context, target context and attack/behaviour context. We will also keep detection 
probabilities or confidence values as supporting information. These values will be used in the correlation 
calculation only if we can show experimentally that they help. 
When we have two detected events, A and B we will compute a similarity value S_i(A,B) for each chosen 
contextual criterion i. The similarity function changes with the type of information we compare. 
Temporal similarity shows how close the event timestamps are. Source/identity similarity shows links 
such as a shared source IP or session when we can find one. Target similarity compares the web resources 
or URIs that the attacks targeted. Attack/behaviour similarity shows how the predicted attack labels or 
behaviours are related. 
We will not set the importance of the selected correlation criteria with fixed weights. Instead the adaptive 
weighting stage will use the method described by Sun, Gu and Chen [4]. That method uses Conditional 
Rough Entropy and Knowledge Granularity to find  how important each alert attribute is from the data. 
Component 1 will adapt that weighting idea to the attributes of the detected HTTP web-attack events.

The correlation stage will be made as a Python module that comes after the multi -label detection stage. 
It will output a group or scenario identifier the member events that belong to that group, the detected

larger forensic investigation framework.

3.5 Baseline / Benchmark 
To evaluate the effect of the proposed weighting mechanism the adaptive contextual correlation 
approach will be compared with a fixed or equal -weight correlation baseline. Both methods will work 
on the set of detected web -attack events. They will also use the contextual criteria, similarity functions 
and threshold-testing procedure. 
In the baseline method every selected contextual criterion will be given the fixed weight. In the proposed 
method the weights for each criterion will instead be determined from data using Conditional Rough 
Entropy and Knowledge Granularity [4]. The correlation score in both cases will then be computed using 
the weighted similarity formula. 
By keeping all correlation criteria and similarity calculations the same across both approaches the 
comparison is designed to focus on the impact of the weighting method. This setup allows the study to 
check whether adjusting the importance of criteria bas ed on data provides an advantage, over giving 
each criterion the same fixed importance when linking detected web-attack events.

3.7 Validation Strategy 
We will validate the detection stage with held-out test data that were not used during the training of the 
Logistic Regression classifiers. Detection performance will be measured by Precision, Recall F1 -score 
per label Micro and Macro averages and Hamming Loss as defined in Section 3.6. 
In the correlation stage we will compare the proposed weighting approach with the fixed/equal -weight 
correlation baseline. Both approaches will use the detected events, contextual criteria, similarity 
functions and threshold-testing procedure so that the effect of the adaptive weighting mechanism can be 
examined under consistent experimental conditions. 
We will analyse correlation threshold values to find an appropriate threshold for grouping sufficiently 
related detected events. The final criterion,  for assessing the quality of the resulting correlated event 
groups will be set based on the dataset evidence and the finalized experimental validation strategy.

Development will proceed iteratively:The development process will consist of five prototypes: 
Prototype 1 – Data Preprocessing and Feature Encoding 
The SR-BH 2020 dataset will be prepared through data cleaning, missing-value handling, relevant

Prototype 4 – Adaptive Attribute Weighting

4. HIGH-LEVEL SYSTEM ARCHITECTURE 
4.1 Overview 
Component 1 is an Adaptive Web Attack Detection and Correlation Model. It works with HTTP request 
data to detect types of web attacks. It keeps contextual details and connects related attack events using 
adaptive weights that come from the data itself. 
The process starts with HTTP web -server logs taken from the SR -BH 2020 dataset [1] [2]. These logs 
go through a preprocessing step. This includes cleaning the data dealing with missing values selecting 
features transforming certain text-based features using TF-IDF and converting some categorical features 
using One-Hot Encoding. 
After preprocessing the data is fed into a One -vs-Rest Logistic Regression model. This model detects 
types of web attacks at once. It gives out predicted attack labels, the probability for each label. Keeps 
important contextual information such as the time stamp, the source or identity of the request the target 
or URI and details about the attack or behavior. 
The detected events are then processed in two steps: contextual similarity calculation and adaptive 
weight calculation. Contextual similarities are calculated based on four criteria: time, source or identity, 
target and attack or behavior. At the time Cond itional Rough Entropy and Knowledge Granularity [4] 
are used to derive data-driven weights for each of these criteria. 
These similarities and weights are combined to compute a weighted correlation score, for each pair of 
events. This score is compared to a correlation threshold. If the score is high enough the events are 
grouped together into event groups or scenarios. The final output includes the grouped events their attack 
labels, the grouping information and the relevant context that led to the correlation. 
4.2 Overall Integration 
Component 1 is one part of a four‑piece CTI‑Assisted Digital Forensic Investigation Tool that small and 
medium businesses can use. Component 1 looks for web attacks. Links them together based on the 
context using data from HTTP requests. 
Inside the system Component 1 creates organized correlated findings about web attacks. These findings 
can be combined with the results and analysis from the parts of the research. The organized output from 
Component 1 will contain: 
• detected web‑attack label(s). Associated probability/confidence information; 
• relevant temporal source/identity, target and attack/behaviour context; 
• correlation score; 
• group/scenario identifier; and 
related member events and correlation information. 
Component 1 supplies the part of the research that finds and links web attacks. The other parts handle 
network analysis, CTI‑assisted analysis and forensic investigation. When the outputs from all parts are 
combined the entire system gives more organized i nformation, for investigating cyber incidents and 
digital forensics.

5. USER REQUIREMENTS 
The user requirements for the proposed component are currently defined as requirements. These 
preliminary requirements are based on the research objectives the proposed methodology and the 
expected integration with the system. These requirements are not ye t confirmed. They do not reflect 
inputs from stakeholders or domain experts. Validation through stakeholder or domain -expert 
involvement will take place during the development and evaluation stages. Therefore the requirements 
presented in this section should not be interpreted as validated requirements. They are still in a stage and 
may change based on further feedback. 
5.1 Preliminary Functional Requirements 
• FR1: The component shall preprocess HTTP request records using the selected fields from the SR -
BH 2020 dataset. 
• FR2: The component shall generate multi -label web-attack predictions using One-vs-Rest Logistic 
Regression and provide probability or confidence information for each predicted attack label. 
• FR3: The component shall retain temporal, source/identity, target, and attack/behaviour contextual 
information from detected events for subsequent correlation. 
• FR4: The component shall calculate contextual similarities between detected events using four 
criteria: temporal, source/identity, target, and attack/behaviour similarity. 
• FR5: The component shall derive adaptive criterion weights using Conditional Rough Entropy and 
Knowledge Granularity. 
• FR6: The component shall calculate a weighted correlation score using the contextual similarity 
values and their corresponding adaptive weights. Detected events that satisfy the selected correlation 
threshold shall be grouped as related events. 
• FR7: The component shall generate correlated web -attack findings containing the information 
required for integration with the overall system. 
 
5.2 Preliminary Non-Functional Requirements 
The following non -functional requirement categories are considered relevant, to the proposed 
component: 
Reproducibility: The processing and evaluation procedures should be clearly documented. This 
documentation must support reproduction of the research results. 
Reliability: The component should process the selected data consistently. It should produce outputs 
without unexpected processing failures. 
Security: Experimental data and generated outputs should be handled securely. They should also be 
stored securely during development and evaluation. 
Usability: The generated correlated web -attack findings should be presented in an understandable 
format. This format should support analysis and system integration. 
Performance: The component should provide processing performance on the available development 
hardware.

6. COMMERCIALIZATION PLAN 
 
6.1 Target Market and Customer Persona 
Target market: 
• medium‑sized businesses (SMEs). 
• Organizations operating web. Web‑based services. 
• Organizations without Security Operations Center (SOC) or specialized security teams. 
Customer persona: 
An SME IT or security administrator who needs to detect web requests and identify related web attack 
events without deploying complex and costly enterprise‑level security infrastructure. 
6.2 Value Proposition 
The component provides multi‑label web attack detection and adaptive contextual correlation of 
malicious HTTP events.Of presenting detected web attacks only as isolated events the component uses 
contextual information such as time, source identity, target resource and attack behaviour to determine 
whether detected events are related. 
The adaptive correlation mechanism uses Conditional Rough Entropy and Knowledge Granularity to 
derive data‑driven attribute weights reducing dependence on fixed correlation weights. 
This provides SMEs with structured and explainable information about related web attack activity for 
security analysis and investigation. 
6.3 Revenue Model 
Potential revenue models include: 
• Subscription‑based web security monitoring. 
• Software‑as‑a‑Service (SaaS). 
• Licensing to SME‑focused IT and cybersecurity service providers. 
• Integration with managed security services. 
• Integration as a security analysis component within the CTI‑assisted digital forensic investigation 
tool. 
6.4 Cost Estimation 
The component will primarily use existing computing resources, open‑source technologies such as 
Python, Pandas, Scikit‑learn and Jupyter Notebook or a suitable IDE with the publicly available SR‑BH 
2020 multi‑label web attack dataset. 
Therefore no significant hardware, software licensing or dataset acquisition costs are expected during 
the research and development stage.Potential future cost areas may include cloud or server infrastructure, 
additional storage, deployment infrastructure, security  testing and maintenance if the solution is 
deployed at a scale. However these resources are not essential for the implementation and evaluation of 
Component 1. Where possible open‑source technologies and existing resources will be used to minimize 
development costs.
